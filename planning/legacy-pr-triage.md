## Experimental code and compatibility hazards

These observations explain why an attractive behavior is not a merge recommendation:

- #40's variable detector uses a global regular expression (`/gm`) with stateful `.test`; path lookup
  assumes every intermediate object exists. `CodeVariableInput` ignores its child field, contains
  Google Maps/test placeholders and commented controls. Its Defer form reads `eventCallback` but
  writes `preInputObservableCreation`. Shared context injection is not uniformly applied: Map and
  Filter still use ordinary `new Function`. The BufferWhen pre-hook is a TODO. There is no execution
  sandbox, migration, isolation test, or explicit initialization contract.
- #40's generator handles only a few creation cases, leaves Merge logic/commented branches unfinished,
  and `generateCreationElementCode` logs without returning code. Connecting a line writes that return
  value into `eventCallback`; this cannot be treated as working generated code.
- #42's Defer/From forms write `input` while displaying `observableFactory`/
  `inputCallbackExpression`; From explicitly notes that switching code is buggy. Buffer model/form
  fields use `closingSelectorExpression` while factories read `projectExpression`. Of permits
  strings but spreads `items` without an explicit expression evaluation contract. IIf compiles its
  condition from the original properties instead of the merged override properties. Override
  propagation differs across joins, so a single consistent parameter rule cannot be inferred.
- #42's generator inserts/clears callback skeletons during connection edits. It is not full graph
  export and may destroy authored expressions. Its `next` helper name is not main's
  `createObservable` helper. Main already has the relevant forms/factory structure with subsequent
  fixes; the branch's old model shapes are not a migration spec.
- #50 adds a Subscribe result drawer and export but does not wire it into OperatorDrawer's dispatch;
  Subscribe in `FlowValueType` is commented. `branchId` can be shared across references and raw errors
  receive fresh branch IDs. Thus it does not define distinct branch/subscription/error correlation.
  Graph dependencies become an array without the prior Set's deduplication.
- #50's AnimationScheduler builds/accumulates animations and logs them without a playback lifecycle;
  the slice contains parallel queues and commented experiments. `selectNextAnimations` shifts
  `state.animations`, not `simulation.animations`, and mutates in a selector. Per-event timestamps
  do not enforce the per-line spacing promised in `req.md`. Disabled props change themes but do not
  enforce mutation restrictions or retain the run lock through the animation drain.

Existing IndexedDB diagrams, Worker-cloneable data, public callbacks, expression helper names and
current ID/dependency semantics must survive future implementation or receive an explicit versioned
migration. Transient event nodes, queues, Worker handles and execution state must stay out of the
versioned diagram schema. No executable prototype, fixture, or test is added by this step.

Questions for 3.2 (not answered by the prototypes):

1. Which events are emitted per subscription, and how are complete, explicit unsubscribe and
   cancellation of a losing/inner branch distinguished? What is the relation between value ID,
   subscription ID, branch ID and dependencies for aggregation and error recovery?
2. Is time virtual, run-relative or wall-clock? What ordering is deterministic across branches?
   How should dropped visual dependencies release waiting events without misleading the user?
3. Should line kinds be derived from endpoints or persisted? Which non-color labels/legend and
   reduced-motion representation convey lifecycle? Does viewer readiness require a graph snapshot?
4. Which edits are blocked during execution and pending animation drain, and which inspection,
   navigation and controls remain available? What exact condition unlocks the graph?
5. Do current 16-group/100-result bounds suffice for protocol/history work? What truncation signal
   is needed, and what per-event/path-size or engine bookkeeping limits remain unmeasured?

Questions for 3.3:

1. Is context per run, diagram, subscription or branch? Who initializes it, when, and how do
   concurrent callbacks, cancellation, restart, exceptions and fallback affect it?
2. Which variable/function signatures are supported? Which cases require context instead of explicit
   invocation parameters? Are pre-hooks useful enough to justify a separate API?
3. How are literal/expression modes serialized, defaults and missing/invalid values handled,
   overrides scoped and validated, and old diagrams migrated? Must unpublished branch-only shapes
   be importable? How is Date represented without relying on a live object?
4. What trust policy applies to local and imported diagrams, network access, Worker execution,
   fallback and synchronous infinite loops? What restrictions block public sharing?
5. Which graph constructs can export faithfully, how are names made deterministic and valid,
   and how are unsupported constructs diagnosed? Should callback scaffolding be opt-in and preserve
   authored code across reconnection, undo and reload?
